# 后端模块检查与优化（2026-10-20）

## 本轮已调整

1. **书库缓存与并发**：原来解析整个 TXT/EPUB 时持有 Reader 全局锁，其他书籍的缓存命中也需要等待。现在只在读写缓存元数据时持锁，同一本书的并发解析合并，不同书最多两路解析。
2. **内存边界**：缓存改为最多四本、估算内容总量最多 64 MiB，并按最近使用顺序淘汰。超大结果不留在缓存；章节标题复制为独立字符串，避免小标题间接保留整本小说的解码缓冲。图片读取最多同时四路，每张仍限制 40 MiB；排队请求可以取消。这里限制的是缓存内容及读取并发，并非整个进程的硬内存限制。
3. **来源服务共享**：浏览、订阅更新、种子获取复用一个动漫来源服务，使浏览与后台刷新能够使用同一来源缓存。网络地址校验、代理和重定向规则保持现有行为。
4. **后台任务生命周期**：新增 taskgroup，统一管理动漫更新、下载、追剧、整理和书库扫描。服务停止后拒绝新后台任务、取消已有任务，并等待退出。书库扫描不再脱离服务使用独立的 Background 上下文。

## 验证

- 单元测试覆盖缓存淘汰、文件版本失效、缓存字节预算、文本编码与章节、EPUB 顺序和脚本过滤、路径穿越拒绝。
- 后台任务测试覆盖取消、等待退出、超时和并发提交，重复执行检查稳定性。
- 编译和 go vet；实际服务继续使用项目 data、5174/18080 和现有书库。
- 本轮没有做数据库迁移，没有修改账号、配置、订阅、密钥或源书籍。

## 后续应基于测量决定的工作

- SQLite 目前单连接串行访问。先统计接口延迟和数据库等待时间，再决定是否增加独立只读连接；直接扩大写连接池容易增加锁竞争。
- 图片响应、来源网络请求和数据库等待值得补充轻量指标。现在没有生产负载数据，不能给出吞吐量提升比例。
- 动漫来源的 HTTP Transport 当前按请求创建。若后续测量显示握手占比较大，可针对可信来源复用连接，但需要保持 DNS、代理和重定向防护。
- HTTP 层已按业务拆分文件，暂不需要为模块数量引入独立服务。后续新增能力应继续保持路由、业务与存储边界。
